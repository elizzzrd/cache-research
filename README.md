# Исследование алгоритмов вытеснения в многоуровневом кеше

Симулятор сравнивает политики замещения страниц и их сочетания
в иерархии из нескольких уровней. При одинаковой суммарной ёмкости исследуются число уровней, выбор политики на каждом уровне и порядок этих политик.

**Критерий качества — доля системных попаданий. Ёмкость делится поровну между уровнями во всех экспериментах.** Эталон — отдельный идеальный кеш той же общей ёмкости, работающий с полной последовательностью запросов.


## 1. Вопросы исследования

1. Даёт ли два уровня с одной и той же политикой больше попаданий, чем один уровень с этой политикой и той же общей ёмкостью?
2. Как зависит доля системных попаданий от числа уровней однородной иерархии при фиксированной общей ёмкости и равном её распределении? Какое из допустимых чисел (при которых число страниц на уровне натуральное) уровней даёт лучший результат?

3. Какая политика лучше, если для каждой выбрать её лучшее число уровней?
4. Улучшают ли результат смешанные иерархии и влияет ли порядок политик?


## 2. Модель системы

| Обозначение | Смысл |
|---|---|
| `С` / `total_capacity` | Суммарное число мест для страниц во всех уровнях |
| `K` | Число уровней; L1 — первый проверяемый уровень |
| `С_i` | Ёмкость уровня i |
| `N` | Число запросов |
| `H` | Число системных попаданий |
| `M` | Число загрузок из источника |


Правила обработки запросов:

- Сначала проверяется L1; при промахе проверяется следующий уровень.
- Уровни ниже найденной страницы не посещаются.
- Страница, полученная снизу, сохраняется в каждом верхнем уровне, на котором этот запрос дал промах. 
- Если промахнулись все уровни, загрузчик получает страницу из источника.
- Вытеснение на одном уровне не вызывает специального переноса или удаления страницы на другом уровне.
- Страница может находиться одновременно на нескольких уровнях. Включение одного уровня в другой не гарантируется.
- История ключей, например ghost-списки, не содержит самих страниц. Обращение к ghost-ключу является промахом данного уровня.
- Системное попадание — запрос, обслуженный без обращения к источнику.


*Одинаковая сумма ёмкостей не гарантирует одинаковое количество различных хранимых страниц: копии на разных уровнях занимают отдельные места. Поэтому добавление уровней может ухудшить результат.*

Все кеши начинают работу пустыми. Начальные промахи включаются в статистику. Страницы имеют одинаковую стоимость хранения. Не моделируются задержки доступа, запись на диск, предвыборка и стоимость метаданных. 


## 3. Краткие принципы алгоритмов

**LRU — Least Recently Used**

Вытесняет страницу, к которой дольше всего не обращались.

- **Попадание:** страница перемещается в начало списка.
- **Промах:** страница загружается и добавляется в начало списка.
- **Вытеснение:** если свободного места нет, удаляется страница из конца списка.

**ARC — Adaptive Replacement Cache**

Использует четыре списка:

| Список | Содержимое |
|---|---|
| `T1` | Недавно загруженные страницы |
| `T2` | Страницы, выделенные как повторно используемые |
| `B1` | Ключи страниц, вытесненных из `T1` |
| `B2` | Ключи страниц, вытесненных из `T2` |

`T1` и `T2` содержат сами страницы. `B1` и `B2` содержат только ключи: они позволяют учитывать историю обращений, но не могут вернуть страницу без загрузки.

Параметр `p` задаёт целевой размер `T1` и регулирует распределение места между недавно поступившими и повторно используемыми страницами.

Обработка запроса:

- **Попадание в `T1`:** страница перемещается в начало `T2`.
- **Попадание в `T2`:** страница перемещается в начало `T2`.
- **Ключ найден в `B1`:** происходит промах; `p` увеличивается, страница загружается и помещается в `T2`.
- **Ключ найден в `B2`:** происходит промах; `p` уменьшается, страница загружается и помещается в `T2`.
- **Ключ отсутствует во всех списках:** новая страница загружается в `T1`.

При освобождении места алгоритм выбирает между вытеснением из `T1` и `T2`, учитывая `p` и тип запроса. История вытеснений хранится в `B1` и `B2` и также ограничена по размеру.

**2Q — Two Queues**

Использует три очереди:

| Очередь | Содержимое |
|---|---|
| `A1in` | Новые страницы; порядок FIFO |
| `Am` | Повторно используемые страницы; порядок LRU |
| `A1out` | Ключи страниц, вытесненных из `A1in` |

Обработка запроса в описанном варианте:

- **Новый ключ:** страница загружается в `A1in`.
- **Попадание в `A1in`:** страница перемещается в начало `Am`.
- **Попадание в `Am`:** страница перемещается в начало `Am`.
- **Ключ найден в `A1out`:** происходит промах; страница загружается и помещается в `Am`, а ключ удаляется из истории.

При вытеснении из `A1in` удаляется самая давно добавленная страница, а её ключ сохраняется в `A1out`. При вытеснении из `Am` удаляется самая давно не использовавшаяся страница. При переполнении `A1out` удаляются старые ключи.

**LFU — Least Frequently Used**

вытесняет страницу с наименьшей частотой обращений.

Для каждой резидентной страницы хранится счётчик:
- при загрузке страницы он устанавливается в 1;
- при попадании увеличивается на 1.

Страницы с одинаковой частотой объединены в списки. При необходимости
освободить место выбирается список с минимальной частотой. Внутри него
вытесняется самая давно не использовавшаяся страница — применяется
правило LRU.

В реализации используются:
- `freq_buckets_` — списки страниц, сгруппированные по частоте;
- `index_` — поиск страницы по ключу;
- `min_freq_` — минимальная частота среди резидентных страниц.

Старение счётчиков не применяется. После вытеснения частота страницы
забывается; при повторной загрузке счётчик снова начинается с 1.

**LIRS — Low Inter-reference Recency Set**

учитывает повторное использование страниц: насколько много
различных страниц встречается между повторными обращениями.

Страницы разделяются на две группы:
- LIR — страницы, которым отводится основная часть ёмкости;
- HIR — страницы, которым отводится оставшаяся часть ёмкости
  и среди которых выбираются жертвы вытеснения.

Алгоритм использует две структуры:
- стек `S` хранит порядок обращений к LIR-страницам и части
  HIR-страниц, включая записи о вытесненных страницах;
- очередь `Q` хранит резидентные HIR-страницы в порядке
  давности обращений.

Обработка запроса:
- попадание в LIR перемещает страницу на вершину `S`;
- обращение к HIR, присутствующей в `S`, повышает её до LIR;
  при превышении лимита нижняя LIR-страница понижается до HIR;
- попадание в резидентную HIR, отсутствующую в `S`,
  обновляет её положение в `Q` и добавляет её на вершину `S`;
- обращение к нерезидентной странице требует загрузки
  и считается промахом.

После первоначального заполнения LIR-группы новые страницы,
отсутствующие в истории, поступают в HIR-группу.

При необходимости освободить место вытесняется страница
из конца `Q`. Если её ключ остаётся в `S`, сохраняется
нерезидентная запись; иначе запись удаляется полностью.

Обрезка стека удаляет нижние HIR-записи до тех пор,
пока внизу не окажется LIR-страница. Нерезидентные записи,
удалённые из стека, также удаляются из таблицы.

**Идеальное кэширование — алгоритм Белади**

- **Попадание:** страница возвращается из кэша.
- **Промах:** страница загружается.
- **Вытеснение:** удаляется страница, следующее обращение к которой находится дальше всего в будущем. Страницы, которые больше не понадобятся, подходят для вытеснения в первую очередь.

В эксперименте идеальный кэш имеет ёмкость `C` и обрабатывает исходную последовательность запросов. Его результат используется как эталон для сравнения с исследуемой иерархией.

## 5. Форматы и запуск

Конфиг содержит число уровней и ровно столько названий, от L1 к последнему уровню:

```text
3
ARC 2Q LRU
```

Входной файл содержит С, N и ровно N целочисленных ключей:

```text
24 8
1 2 1 3 4 1 2 5
```

Пробелы и переводы строк равнозначны. Проверяются неправильные числа, переполнение,
нехватка и избыток данных. Для эксперимента требуется N > 0 и положительная
ёмкость каждого уровня. 

Команды выполняются из корня проекта в Linux:
```bash
make gtest
make
./build/cache configs/full/lru_arc.cfg < experiments/data/hot8_scan_c24_seed42.in
```

Для модульных тестов используются Google Test и готовый `main()` из `gtest_main`.
Цели `make gtest`, `make testrun` и `make check` запускают модульные тесты.

## 6. Метрика и условия сравнения

Основной показатель - `hit_rate`:
$$
h = \frac{H}{N} = 1 - \frac{M}{N}.
$$

Отставание от эталона:
$$
d = h_{\mathrm{ideal}} - h = \frac{M - M_{\mathrm{ideal}}}{N}.
$$

`excess_source_loads` = `source_loads - ideal_source_loads`


Во всех сравниваемых запусках одинаковы С, N, порядок ключей, правила заполнения
и начальное пустое состояние. Изменяется только изучаемая конфигурация.
Нижние уровни получают отфильтрованный верхними уровнями поток: это часть модели.

Файл результатов содержит `config`, `input`, `policies`, `levels`, `capacities`,
`total_capacity`, `requests`, `system_hits`, `source_loads`, `hit_rate`,
`ideal_hits`, `ideal_source_loads`, `ideal_hit_rate`, `excess_source_loads`.


## 7. Набор нагрузок

Метрика задаёт, что измеряется; нагрузка задаёт, на каких запросах измеряется.
Одна метрика не заменяет разные условия работы. Для исследования
выбраны **две основные нагрузки**:

| Нагрузка | Как формируется | Зачем нужна |
|---|---|---|
| `hot8_scan` | Четыре случайных обращения к восьми постоянным частым ключам, затем новый ключ | Поведение при устойчивом частом наборе и потоке одноразовых страниц |
| `phases24` | Четыре фазы с разными частыми наборами по 24 ключа; вероятность фонового запроса 5% | Поведение при изменении характера обращений |

### Эксперимент 1. Один уровень против двух

Для каждой политики P сравниваются `(P)` и `(P, P)` при общей ёмкости С.
Например, `ARC(24)` сравнивается с `ARC(12) + ARC(12)`.
Смешанные пары здесь не рассматриваются: сначала выделяется влияние разделения одной и той же политики на два уровня.

Результат: `h(P, 1)`, `h(P, 2)` и разность в процентных пунктах для каждой нагрузки.


### Эксперимент 2. Число уровней для одной политики

Для каждой P исследуются `(P)`, `(P,P)`, `(P,P,P)`, `(P,P,P,P)`.
Результаты K=1 и K=2 берутся из первого эксперимента. Новые запуски нужны только для K=3 и K=4.


Для каждой нагрузки определяется лучшее число уровней:

$$
K_P^* = \min\operatorname*{max}_{K\in\{1,2,3,4\}} h(P,K).
$$

Если лучший результат
получен при K=4, не утверждается, что дальнейшее увеличение обязательно ухудшает
результат: более глубокие иерархии не исследовались.

### Эксперимент 3. Политики при своих лучших K

Сравниваются `h(P, K_P*)` для разных P на одной и той же нагрузке. Рядом
указываются K*, результат одноуровневого LRU и IdealCache. 


### Эксперимент 4. Сочетания и порядок политик

Для K=2,3,4 перебираются все упорядоченные сочетания выбранного набора политик.
Однородные комбинации уже измерены; дополнительные запуски нужны для смешанных.

Лучшая смешанная комбинация сравнивается с лучшей однородной:

1. при том же K — влияние сочетания политик без изменения числа уровней;
2. среди всех исследованных K — лучшая найденная конфигурация в выбранном диапазоне.

Пары `(P,Q)` и `(Q,P)` сравниваются отдельно. Для трёх и четырёх уровней порядок
тоже сохраняется. Нельзя ограничивать смешанные варианты только глубиной,
победившей в однородных иерархиях: у смеси может быть другой лучший K.
